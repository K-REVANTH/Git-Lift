# Azure DevOps (ADO) → GitHub Enterprise Cloud (GHEC) Metadata Migration / Parity Report

## 1. Executive Summary

This report presents an exhaustive metadata-level parity analysis between Azure DevOps Services (ADO) and GitHub Enterprise Cloud (GHEC), performed to support the engineering design of a custom migration solution. The analysis covers organization structure, projects, repositories, branches, pull requests, work items, boards, pipelines, artifacts, packages, security, governance, testing, wikis, integrations, and all associated metadata, permissions, configuration, and historical data.

**Master Inventory Scale:** The complete master inventory developed for this analysis contains **213 distinct metadata/capability items** spanning 22 major categories. Each item has been individually researched against official Microsoft Azure DevOps Services documentation and official GitHub Enterprise Cloud documentation, classified into exactly one of three categories, and will appear in exactly one of the three responses.

**Classification Distribution Summary:**

| Classification | Count | Description |
|---|---|---|
| 🟢 Seamless / Direct | 38 | Metadata transferable without meaningful transformation of data model, scope, semantics, or behavior |
| 🟡 Migratable with Changes | 131 | Both platforms have comparable capability but require transformation of data model, scope, configuration, permissions, or behavior |
| 🔴 Hard Blockers | 44 | No meaningful native GHEC equivalent; original ADO behavior cannot reasonably be represented |

**Key Structural Finding:** The most fundamental challenge is the organizational hierarchy mismatch. ADO uses a three-level hierarchy (Organization → Project → Repository/Team) where the **Project** is the primary unit of work-item management, board configuration, pipeline organization, and permission scoping. GHEC uses a different hierarchy (Enterprise → Organization → Repository) with **no native Project-as-container concept** equivalent to ADO Projects. GitHub Projects (the planning tool) are a lightweight planning layer, not a structural container. This mismatch cascades through virtually every metadata category.

**Key Data Model Findings:**
- Git repository data (commits, branches, tags, LFS objects) migrates with high fidelity.
- Pull request data can be migrated but reviewer semantics, voting model, and completion behavior differ significantly.
- Work items require deep transformation: ADO's rich typed work-item system with custom processes, area/iteration paths, state transitions, custom rules, and hierarchical relationships has no structural equivalent in GHEC Issues/Projects.
- Azure Pipelines → GitHub Actions requires complete rewrite; there is no configuration-level migration path.
- Permissions require fundamental restructuring due to different inheritance models, scope models, and role definitions.
- Historical data (work-item revisions, build logs, deployment history, audit logs) is largely non-migratable into native GHEC structures, though it can be preserved externally.

## 2. 🟢 Seamless / Direct Migrations

The following table identifies ADO metadata/capabilities that can be migrated to GHEC without meaningful transformation of data model, scope, configuration, permissions, semantics, or behavior. "Seamless" means the source data can be transferred to the target with only mechanical API-level mapping (e.g., REST call syntax differences) and the resulting target-side entity faithfully represents the source entity.

## 3. 🟡 Migratable with Changes / Behavioral Differences

The following table contains all metadata/capabilities where both Azure DevOps Services and GitHub Enterprise Cloud offer comparable functionality, but where migration requires transformation of data model, scope, configuration, permissions, semantics, or behavior. Data can be preserved and equivalent target-side configuration can be established, but engineering effort is required to translate between the platforms.

## 5. Conditions and Assumptions

### 5.1 Conditions Applicable to Seamless Items

1. **Git Data Transfer Mechanism:** All Git-native data items (commits, branches, tags, LFS pointers/objects, submodules, .gitignore, .gitattributes, LICENSE, README, wiki repo) assume migration via standard Git protocol operations (`git clone --mirror` / `git push --mirror` or equivalent). This is the most reliable mechanism for preserving Git data fidelity.

2. **LFS Storage Quotas:** GHEC includes 1 GB of LFS storage and 1 GB/month bandwidth per account by default, with additional data packs purchasable. Large LFS repositories may require purchasing additional storage before migration. Per-file limit on GHEC is 2 GB. ADO has a 50 GB repository size limit (which includes LFS). Verify that the total LFS object store size for each repository fits within GHEC quotas or that sufficient data packs are provisioned. (Source: GitHub Docs — "About storage and bandwidth usage")

3. **Repository Size Limits:** GHEC recommends repositories remain under 5 GB of Git data (excluding LFS). ADO permits repositories up to 250 GB (though Microsoft recommends keeping them under 10 GB for performance). Repositories exceeding GHEC's recommended size may experience degraded performance. There is a hard push limit of ~100 MB per file in standard Git on GitHub (LFS should be used for larger files). (Source: GitHub Docs — "About large files on GitHub")

4. **Identity Mapping Prerequisite:** Items referencing user identities (PR creator, comment authors) require a pre-established identity mapping between ADO user identities (typically Microsoft Entra ID UPNs or Microsoft Account emails) and GHEC user accounts (GitHub usernames). Without this mapping, user references can be stored as text annotations but will not link to active GHEC user profiles. The identity mapping is a prerequisite for faithful migration of all user-referencing metadata.

5. **Organization Name Compatibility:** GHEC organization names must be 1-39 characters, alphanumeric or hyphens, cannot start/end with a hyphen, and cannot contain consecutive hyphens. ADO organization names have different restrictions. If an ADO org name does not meet GHEC requirements, a compatible name must be chosen. (Source: GitHub Docs — "Creating a new organization from scratch")

6. **Repository Name Compatibility:** GHEC repository names can contain alphanumeric characters, hyphens, underscores, and periods. They cannot begin with a period, and `.git` and `.github` have special meanings. ADO repository names permit most Unicode characters including spaces. Repository names containing characters not supported by GHEC require sanitization. (Source: GitHub Docs — "Creating a new repository")

7. **Fork Relationship Establishment:** To preserve fork relationships, the parent (upstream) repository must be migrated to GHEC first. Forks must then be created using the GitHub Fork API (`POST /repos/{owner}/{repo}/forks`), and the forked content pushed. Simply pushing the same content to an independently created repository does not establish a fork network relationship in GHEC. (Source: GitHub Docs — "Fork a repo"; GitHub REST API — "Create a fork")

8. **Markdown Dialect Compatibility:** While core Markdown transfers seamlessly, content using ADO-specific Markdown extensions will render differently on GHEC. Known differences:
   - ADO `[[_TOC_]]` → No GFM equivalent (omitted in rendering)
   - ADO `::: mermaid` → GFM ` ```mermaid ``` `
   - ADO `@<GUID>` person mentions → GFM `@username` mentions
   - ADO `#123` work-item links → GFM `#123` issue links (different target entities)
   - ADO `![text](/.attachments/image.png)` → URL needs remapping

   These differences are cosmetic/syntactic for the base content and do not prevent transfer.

9. **Wiki Repository Structure:** ADO wikis use `.order` files to define page ordering within folders. GHEC wikis use `_Sidebar.md` for custom navigation and alphabetical ordering by default. Page ordering metadata from `.order` files should be translated into a `_Sidebar.md` navigation structure. Page files themselves (`.md`) transfer directly. (Source: Azure DevOps Docs — "Provisioned vs. published wikis"; GitHub Docs — "Adding or editing wiki pages")

10. **Attachment Size Limits:** GHEC issue/PR attachments are limited to 25 MB per file (10 MB for images in some contexts). Videos up to 100 MB are supported. ADO has a 60 MB per-attachment limit. Attachments exceeding GHEC limits cannot be uploaded and would need alternative hosting. (Source: GitHub Docs — "Attaching files")

11. **Azure DevOps Services Scope:** This analysis is scoped to Azure DevOps Services (cloud). Capabilities specific to Azure DevOps Server (on-premises) or legacy TFS are excluded unless explicitly noted. For example, TFVC (Team Foundation Version Control) is available in ADO Services but is a different source-control type than Git; TFVC repositories are addressed in the Behavioral Differences section. (Source: Microsoft Docs — "Azure DevOps Services vs. Azure DevOps Server")

12. **GHEC Enterprise Tier:** This analysis assumes GHEC with Enterprise licensing. Features requiring GitHub Advanced Security (GHAS) — such as CodeQL code scanning, secret scanning with push protection, and dependency review — require GHAS licensing which is an additional purchase on top of GHEC. Items requiring GHAS are noted in their respective entries. (Source: GitHub Docs — "About GitHub Advanced Security")

### 5.2 Conditions Applicable to Behavioral Differences

1. **Custom Migration Tooling Required**: All items in this category require custom migration logic. Off-the-shelf tools (e.g., GEI, `azure-devops-migration-tools`) address subsets; a comprehensive migration requires bespoke code for at minimum work items, boards, pipelines, service connections, and permission mapping.

2. **Identity Mapping is a Cross-Cutting Prerequisite**: A definitive mapping between ADO user identities (Entra ID objectId / UPN / MSA) and GHEC accounts (login) must be established before any user-referencing metadata is migrated. Without it, all attributions collapse to a migration bot account. Options: (a) manual CSV mapping; (b) Entra ID SCIM to GHEC EMU for automated mapping; (c) admin-provided mapping API.

3. **Timestamps Cannot Be Backdated Natively**: GHEC REST APIs set `created_at`/`updated_at` to the API call time. To preserve historical timestamps in a visible manner, either (a) prefix them in body text ("Originally posted 2021-03-15 by @jane"), (b) use the GitHub Import API for issues (rate-limited, deprecated for some flows), or (c) accept the migration timestamp with the original captured in metadata.

4. **API Rate Limits Constrain Migration Throughput**: GitHub REST API: 5,000 requests/hour authenticated (15,000 for GitHub App installations on GHEC Enterprise). GraphQL: 5,000 points/hour. Secondary rate limits apply for concurrent requests and content creation. Migration must be batched, backed-off, and potentially spread across multiple GitHub App installations.

5. **GHAS is a Separate Purchase**: Items referencing GitHub Advanced Security (code scanning, secret scanning with push protection, dependency review, custom patterns) require GHAS licensing on top of GHEC Enterprise. Verify licensing before planning security-feature migration.

6. **EMU Decision Impacts Everything**: The choice between standard GHEC and Enterprise Managed Users must be finalized before migration begins. EMU restricts contributor collaboration to enterprise-provisioned identities only; usernames are `_short-code` suffixed; existing GitHub users cannot join an EMU enterprise with their existing accounts.

7. **Rulesets vs. Branch Protection**: For all branch/repo protection items, prefer Rulesets over classic branch protection rules. Rulesets support layering, bypass lists, organization-wide targeting, and multiple rules per branch pattern — the closest structural fit for ADO's overlapping branch policies.

8. **Actions Marketplace Dependency**: Successful pipeline migration depends on availability of GitHub Actions equivalent to ADO tasks. Common tasks (Azure deploy, Docker build, artifact upload) have well-established Action equivalents. Custom or niche tasks may require building custom actions or inlining shell scripts.

9. **Environment Scope is Repo-Local**: GHEC environments are repository-scoped, not organization-scoped. ADO environments shared across pipelines within a project must be recreated in each GHEC repository that deploys to them. Environment secrets/protection rules replicated per repo.

10. **Package Format Coverage Gaps**: GitHub Packages does not natively support Python (PyPI) or Universal Packages. Migration plans for these must include alternate hosting (private PyPI, OCI artifacts, GitHub Releases assets).

11. **Wiki Migration Uses Git**: Wikis are migrated as Git repositories (`<repo>.wiki.git`). The migration is a `git clone` from ADO wiki repo, structural transformation (`.order` → `_Sidebar.md`, Markdown dialect adjustments), and `git push` to GHEC wiki. Wiki must be initialized on GHEC target repo before push (create at least one page in UI first).

12. **Historical Runs / Deployments Not Migrable Natively**: Pipeline run history, build logs, deployment records, test run results, and audit logs cannot be loaded into GHEC's native structures. If historical retention is required, export via ADO REST API and archive externally (blob storage, SIEM, dedicated read-only host).

13. **CODEOWNERS Placement**: For CODEOWNERS-based required reviewer migration, the file must be placed in `.github/`, `docs/`, or repo root, AND the branch protection rule must have "Require review from Code Owners" enabled. Users/teams referenced must have appropriate repo access.

14. **Secret Values Must Be Re-Supplied**: All secrets (variable group secrets, service connection credentials, secure files) require re-entry at the target. Source secret values are not retrievable by API. Coordinate with secret owners; prefer OIDC federation where applicable to eliminate stored credentials entirely.

15. **Merge Queue Consideration**: GHEC merge queue (available on Team/Enterprise) is a strong alternative when ADO branch policies enforce complex build-validation + up-to-date requirements. Consider adopting merge queue where source used aggressive build-validation policies.

### 5.3 Conditions Applicable to Hard Blockers

1. **"Hard Blocker" Scope**: An item is classified as a Hard Blocker when the underlying ADO capability has no reasonable native representation in GHEC — meaning that even with custom code, external storage, and third-party tooling, GHEC cannot reproduce the source behavior within its own platform. Items where data can be preserved externally but native behavior is unavailable are included here because the GHEC experience is fundamentally different.

2. **External Archive as Universal Fallback**: For virtually every blocker involving historical data (audit logs, pipeline logs, deployment history, approval history, work item revisions, test run history, notification delivery), the standard mitigation is export via ADO REST API to an external archive (Azure Blob, S3, SIEM, dedicated read-only host). The archive is not queryable within GHEC but satisfies compliance retention requirements. Plan storage capacity and retention policy accordingly.

3. **Third-Party Tools May Cover Gaps**: Several blockers (test management, dashboards, analytics, symbol serving, artifact proxying) have well-established third-party solutions (TestRail, Xray, Grafana, PowerBI, JFrog Artifactory, Sonatype Nexus). If existing organizational tooling covers the gap, migration risk is reduced. Otherwise, factor tool selection and licensing into the migration budget.

4. **Behavioral vs. Data Loss**: Distinguish between (a) blockers where only historical data is lost (native GHEC equivalent exists going forward — e.g., audit log, deployment history) and (b) blockers where the capability itself is absent (test plans, deny permissions, path-scoped access, Universal Packages). The former is time-bounded; the latter is a permanent capability gap.

5. **User-Owned Data Cannot Be Migrated**: PATs, SSH keys, personal notification preferences, personal queries, personal reactions, personal watch/follow lists are user-owned. Migration requires user action or is simply lost. Communicate expectations before cutover.

6. **Enforcement Guarantee Loss**: Several ADO features (custom rules engine, gated check-ins, deny permissions, TFVC checkin policies) provide server-side enforcement that prevents non-conforming actions. GHEC's model relies on branch protection and post-hoc automation (Actions). Post-hoc enforcement can revert or flag, but cannot prevent the initial action. Compliance regimes that require prevention (rather than detection) must be reviewed.

7. **Path-Scoped Access Model Requires Repo Restructuring**: Both path-scoped repository permissions and area-path-scoped work item permissions require restructuring at the repository level in GHEC. This is an architectural decision affecting how the source is decomposed and cannot be automated as a metadata transformation.

8. **TFVC Migration Is a One-Way Conversion**: TFVC-to-Git migration via `git-tfs` produces Git history with best-effort mapping of changesets to commits. Shelvesets become branches or are discarded; checkin policies do not translate; workspaces have no concept in Git. TFVC users must be retrained on Git workflows.

9. **Test Management Is a Distinct Product Category**: Azure Test Plans is a mature test management product. Its migration is not a metadata transformation but a product replacement — either move to a third-party test management tool integrated with GHEC (TestRail, Xray, Zephyr Scale, qTest) or adopt a lighter issue-based convention with acknowledged fidelity loss.

10. **Dashboard and Analytics Migration Is a BI Project**: Reproducing ADO dashboards, delivery plans, velocity/CFD/burndown widgets, and OData analytics is not a metadata transformation but a business intelligence redesign. Budget separately for BI tool selection (Grafana, PowerBI, Datadog, custom) and data pipeline construction against GHEC GraphQL/REST APIs.

11. **Symbol Server, Universal Packages, and PyPI Require Alternative Hosting**: These package formats/features are not supported by GitHub Packages. Migration means selecting alternative hosting (symbol server, private PyPI, OCI-based generic artifact hosting, or continued use of Azure Artifacts as a limited-scope package host post-migration).

12. **Extension Rewrite Required**: Any custom ADO extensions must be rewritten as GitHub Apps. UI contributions (custom hubs, tabs, form controls, dashboard widgets) do not have equivalents in GHEC's extension model and require external web applications with cross-links from GitHub.

13. **Compliance and Audit Retention**: Where regulatory compliance requires long-term audit retention (SOX, HIPAA, PCI, GDPR), the external archive approach for ADO historical data must satisfy the applicable retention period. Coordinate with compliance/legal before decommissioning ADO.

14. **Feature Parity vs. Migration Feasibility**: Some items in this table (e.g., Discussions, GitHub Community Standards) represent capabilities GHEC has that ADO lacks — these are not migration blockers but they illustrate that platform mapping is bidirectionally asymmetric. Focus on ADO features without GHEC equivalent for blocker classification.

15. **Coexistence Period Recommendation**: For blockers involving features with no direct target (test plans, dashboards, analytics), consider retaining read-only access to the source ADO organization for 90–180 days post-migration. This provides reference access during team transition and reduces urgency of external archive setup.

## 6. Key Migration Observations

### Structural Mapping

- **The single most consequential decision is Organization/Project mapping.** ADO's `Project` is a heavyweight container (repos + work items + pipelines + boards + wiki + artifacts + permissions). GHEC has no equivalent container. Two primary strategies exist:
  - **Strategy A (multi-org): each ADO Project → its own GHEC Organization** within a single GHEC Enterprise. Preserves isolation and per-project admin autonomy. Higher administrative overhead but clearer boundaries. Recommended when ADO Projects have distinct ownership, security, or compliance requirements.
  - **Strategy B (single-org with prefixing): all ADO Projects in one org → one GHEC Organization** with repository naming convention (`<projectName>-<repoName>`) and teams representing projects. Simpler admin surface. Recommended when projects are collaborative and share membership.

- **Teams as permission grouping.** GHEC Teams should be modeled as permission-bearing entities (map to ADO security groups) rather than direct 1:1 copies of ADO Teams (which are also delivery/backlog units). If both semantics matter, create two types: "Permission Teams" (org-wide, grant repo access) and "Delivery Teams" (represented as GitHub Projects with own views and CODEOWNERS entries).

### Work Item Migration

- **Work item migration is the highest-risk, highest-effort area.** Expect that a faithful migration requires (a) mapping WITs to labels + issue types + Projects fields; (b) flattening area path hierarchy to labels or project field values; (c) mapping iteration paths to Project iteration field; (d) recreating custom fields as Project custom fields; (e) converting HTML content to Markdown; (f) preserving history externally (attached as issue asset); (g) rebuilding queries as Project filters.

- **Do not attempt to migrate all historical work items unless necessary.** Consider migrating only open/active work items and archiving closed work items externally (JSON/CSV export). This dramatically reduces migration complexity and API load.

- **Work item ID references break.** All cross-references (in PR descriptions, commit messages, wiki, pipeline definitions, other work items) will need rewriting to reference new issue numbers, or the original IDs must be preserved as searchable text (`AB#12345`).

### Pipeline Migration

- **YAML-to-YAML conversion is not high-fidelity.** Tools that automatically convert Azure Pipelines YAML to Actions YAML produce templates requiring manual completion. Plan for manual pipeline redesign as the norm.

- **Simplify during migration.** Migration is a good opportunity to consolidate multi-stage classic release pipelines and complex YAML into cleaner Actions workflows using reusable workflows and composite actions.

- **OIDC is a first-class opportunity.** Migrate away from stored service connection secrets toward OIDC federation with cloud providers (Azure, AWS, GCP) — reduces secret management burden significantly.

### Permission Migration

- **Deny-based permissions do not translate.** ADO supports explicit deny ACLs; GHEC permissions are additive. Any deny-based governance model must be rethought as least-privilege additive grants.

- **Path-based permissions have no equivalent.** ADO can grant permissions on repo subfolders. GHEC repository access is all-or-nothing per repo. If path-based security is critical, split the repo.

- **Area/iteration path permissions do not translate.** ADO work-item security by area path has no GHEC equivalent. If required, split work items into separate repositories per secured area.

### Branch Policies → Rulesets

- **Prefer Rulesets over classic Branch Protection.** Rulesets support: multiple rules per branch pattern, org-wide application, bypass lists with actor selection, evaluation across repositories. This best matches the layering behavior of ADO branch policies.

- **Convert build validation and status checks last.** These require the corresponding Actions workflows to exist and be named. Migrate workflows first, then set required status checks.

### Data Preservation Trade-offs

- **Data migration ≠ configuration recreation ≠ historical preservation ≠ behavioral parity.** For each item, evaluate all four axes. Many items in this category preserve data and configuration but not history or exact runtime behavior. Communicate this clearly to stakeholders.

- **Historical data preservation via external archive is a valid pattern.** For pipeline runs, deployment records, audit logs, work item revisions, and test results, an external read-only archive (blob storage + search) preserves compliance value without loading GHEC.

### Cutover Strategy

- **Plan for a coexistence period.** During migration, both ADO and GHEC will be active. Establish clear direction: read-only ADO immediately after data migration, with the source retained for reference for 30-90 days.

- **Freeze windows are mandatory for consistent state.** For work items and pipelines, a freeze on ADO during migration is essential to avoid diverging state.

- **Notification cutover is disruptive.** Users must reconfigure watch preferences on GHEC. Provide clear guidance and default subscriptions where possible.

### Observations for Hard Blockers

#### Architectural Implications

- **Some blockers reveal that ADO and GHEC serve overlapping but non-identical purposes.** ADO Services is an integrated ALM platform (SCM + work management + CI/CD + test + artifacts + dashboards + analytics). GHEC is primarily a code and collaboration platform with strong CI/CD and lightweight work management. Migration is not always a full replacement — it is often a decomposition where GHEC replaces the SCM+CI/CD core, and other tools replace test management, dashboards, analytics, and specialized package formats.

- **The blocker inventory should shape organizational tool strategy, not just migration engineering.** Before migration, catalog which blockers matter to each team. Teams heavily dependent on Test Plans, Delivery Plans, or complex custom rules face a different migration than teams that use ADO primarily for Git and Pipelines.

#### Data-Loss Communication

- **Historical data loss must be explicitly acknowledged by data owners.** For each historical-data blocker (work item revisions, pipeline logs, deployment history, audit log, test results), obtain formal acceptance from the owner that native GHEC representation is not available and that the external archive strategy is sufficient.

- **User-owned data loss requires clear user communication.** PATs, SSH keys, notification preferences, and personal queries do not migrate. Users must reconfigure on GHEC. Provide a checklist and support window.

#### Enforcement Model Shifts

- **Preventative → detective control shift is significant.** ADO's rule engine, deny permissions, and gated check-ins prevent non-conforming actions. GHEC's Actions-based automation detects and reacts. Security and compliance stakeholders must understand this shift and re-approve controls accordingly.

- **Least-privilege additive permissions require design work.** Removing deny-based ACLs and redesigning permissions as additive-only teams and roles is an opportunity to clean up permission sprawl — but it is real design work, not a metadata transformation.

#### Test Management Decision

- **The test management decision is often the single biggest organizational change.** Teams using Azure Test Plans extensively face a choice between (a) adopting third-party test management (cost, training, integration work) or (b) shifting testing culture toward code-based automated tests only (cultural change). Neither is a technical migration; both are organizational decisions.

#### Package and Artifact Ecosystem

- **Package migration is per-format.** npm, NuGet, Maven, Docker migrate reasonably to GHCR/GitHub Packages. Python, Universal Packages, symbol server require alternative hosting. Plan per-format migration paths and consumer configuration updates.

- **Artifact proxying via feed upstream sources has no GHEC equivalent.** Organizations relying on Azure Artifacts as a curated proxy for public registries need a dedicated artifact proxy solution (Artifactory, Nexus, ProGet) as part of the GHEC migration.

#### Custom Extension Migration

- **Custom extensions become custom GitHub Apps.** For each ADO extension in use, evaluate whether (a) an equivalent GitHub App exists in Marketplace, (b) it must be rewritten as a GitHub App, or (c) the functionality can be dropped. UI-heavy extensions face the largest rewrite; API/webhook extensions port more directly.

#### Path-Based Access Restructuring

- **Path-based access restrictions require repository architecture changes.** Repos with path-scoped access must be split. This is a code-level and CI-level restructuring, not a metadata operation. Plan submodule strategy or multi-repo tooling for reunification if needed.

#### Cutover Sequencing for Blockers

- **Complete external archives before ADO decommissioning.** For historical audit, pipeline, deployment, and work item data, ensure external archives are complete, verified, and searchable before shutting down the source. Test archive retrieval procedures with compliance and audit teams.

- **Retain source read-only for a defined coexistence period.** 90–180 days of read-only ADO access reduces migration risk and provides reference access. Longer retention may be required by compliance policy.
