# GitLab -> GitHub Parity Report

---

## 1. Executive Summary
This report assesses migration from **GitLab** to **GitHub**. Overall risk is **CRITICAL** with **42** total gaps.

**Key findings at a glance:**

- Hard Blockers: 10
- Behavioral Differences: 24
- Partial Support: 8
- Seamless Migrations: 39

Migration teams should validate blockers, remediate partial support items, and confirm behavioral differences before execution.

## 2. 🔴 Hard Blockers
### 1. Group-Level Labels (`labels.group_level`)
**Category:** labels

**Source behavior:** GitLab allows labels to be defined at the group level. Group labels are inherited by all projects within the group and appear alongside project labels.

**Target behavior:** GitHub labels exist only at the repository level. There is no organization-level label that is inherited by all repositories.

**Impact:** HIGH — GitLab group labels must be manually replicated to each GitHub repository.

**Workaround:** Use GitHub's label management API or a GitHub Action to synchronize a canonical set of labels to all repositories in an organization.

**Remediation effort:** LOW

**Data migration consideration:** Group labels must be replicated to every repository before migrating issues that reference them.

---

### 2. Scoped Labels (`labels.scoped`)
**Category:** labels

**Source behavior:** GitLab scoped labels use the :: separator (e.g., type::bug, type::feature). Within a scope, only one label can be applied at a time — applying a new one removes the existing scoped label.

**Target behavior:** GitHub does not have a native scoped label concept with mutual exclusivity. Labels are flat.

**Impact:** HIGH — GitLab scoped label enforcement semantics are completely lost on migration to GitHub.

**Workaround:** Retain the :: separator in the label name when migrating from GitLab, but mutual-exclusivity enforcement must be implemented via GitHub Actions or external automation.

**Remediation effort:** MEDIUM

**Data migration consideration:** Label names can be migrated as-is. Mutual-exclusivity enforcement must be reimplemented.

---

### 3. Confidential Issues (`pm.confidential_issues`)
**Category:** project_management

**Source behavior:** GitLab issues can be marked as confidential, hiding them from non-member users while remaining visible to project members with Reporter role or above.

**Target behavior:** GitHub does not support confidential issues. All issues in a repository are visible to all repository collaborators with read access. There is no per-issue visibility control.

**Impact:** HIGH — Confidential issue content will become visible to all repository collaborators after migration.

**Workaround:** Use a separate private repository for sensitive issues, or use GitHub's issue-level locking as a partial substitute. Neither fully replicates GitLab's per-issue confidentiality.

**Remediation effort:** MEDIUM

**Data migration consideration:** Confidential issues MUST be handled before migration to prevent accidental exposure.

---

### 4. Time Tracking (`pm.time_tracking`)
**Category:** project_management

**Source behavior:** GitLab has built-in time tracking on issues and MRs using /estimate and /spend quick actions. Total estimated and spent time is displayed on the issue.

**Target behavior:** GitHub does not provide any native time tracking on issues or pull requests. There are no /estimate or /spend commands.

**Impact:** HIGH — All time tracking estimates and spent values from GitLab issues are permanently lost on migration.

**Workaround:** Use third-party GitHub Apps (e.g., ZenHub, Clockify GitHub integration) for time tracking. All GitLab time tracking data is lost during migration unless manually exported.

**Remediation effort:** LOW

**Data migration consideration:** Time tracking data MUST be exported from GitLab before migration; it cannot be imported to GitHub.

---

### 5. Dependency Proxy (`repo.dependency_proxy`)
**Category:** repository

**Source behavior:** GitLab provides a Dependency Proxy for Docker images and package registries, caching upstream images from Docker Hub and reducing rate-limit issues.

**Target behavior:** GitHub does not offer a native dependency proxy or Docker image caching layer for upstream registries.

**Impact:** HIGH — Dependency proxy pipelines must be re-architected to use an external proxy solution.

**Workaround:** Use GitHub Packages as a private registry alongside GitHub Container Registry. Pull-through caching is not natively supported; use third-party proxy solutions (e.g., Nexus, JFrog Artifactory).

**Remediation effort:** HIGH

**Data migration consideration:** No historical data; cached images must be re-pulled from upstream.

---

### 6. Repository Mirroring (`repo.mirroring`)
**Category:** repository

**Source behavior:** GitLab supports push mirroring, pull mirroring, and bidirectional mirroring. Mirrors can be configured per project to remote repositories including GitHub, Bitbucket, and others.

**Target behavior:** GitHub does not have native built-in repository mirroring. Repositories cannot be configured to automatically push to or pull from an external remote.

**Impact:** HIGH — Teams relying on GitLab mirroring must implement GitHub Actions-based mirroring workflows.

**Workaround:** Use GitHub Actions workflows scheduled to periodically push/pull to a remote mirror. Third-party tools (e.g., git-mirror-action) can automate this.

**Remediation effort:** MEDIUM

**Data migration consideration:** No data loss. Git history is fully preserved. The automation layer must be re-implemented.

---

### 7. Merge Trains (`review.merge_trains`)
**Category:** code_review

**Source behavior:** GitLab Merge Trains queue MRs so each is tested against the combined state of all previously queued MRs, preventing broken mainline. Available on GitLab Premium and Ultimate.

**Target behavior:** GitHub does not have a native merge train feature. Pull requests cannot be queued to be tested together against a combined branch state.

**Impact:** HIGH — Teams relying on merge trains for broken-build prevention must adapt to GitHub Merge Queue semantics, which are behaviorally different.

**Workaround:** GitHub Merge Queue (GitHub Enterprise Cloud) provides similar serial-merge guarantees but does not test PRs together before merge; each PR is merged individually after its required checks pass.

**Remediation effort:** LOW

**Data migration consideration:** No data migration needed. Pipeline and workflow strategy must be adapted.

---

### 8. DAST (Dynamic Application Security Testing) (`security.dast`)
**Category:** security

**Source behavior:** GitLab provides DAST scanning (API and web application) as part of GitLab Ultimate. DAST is configured via .gitlab-ci.yml and can run against deployed environments.

**Target behavior:** GitHub does not provide a native DAST scanning solution. There is no built-in dynamic application security testing in the GitHub platform.

**Impact:** HIGH — GitLab Ultimate DAST pipelines must be completely rewritten using third-party tooling.

**Workaround:** Integrate third-party DAST tools (OWASP ZAP, Burp Suite, Checkmarx DAST) as GitHub Actions steps in the CI workflow.

**Remediation effort:** HIGH

**Data migration consideration:** No historical data. CI pipeline configuration must be rewritten.

---

### 9. SAST (Static Application Security Testing) (`security.sast`)
**Category:** security

**Source behavior:** GitLab provides built-in SAST analyzers for many languages as part of GitLab Secure. Results appear in the MR security widget and vulnerability report.

**Target behavior:** GitHub provides CodeQL as its SAST engine via GitHub Advanced Security. CodeQL analyzes code on push/PR and results appear in the Security tab. Configuration via .github/workflows/codeql.yml.

**Impact:** HIGH — GitLab SAST runs as CI jobs; GitHub uses CodeQL Actions which requires pipeline rewrite.

**Workaround:** Enable CodeQL default setup in GitHub repository settings. This automatically creates a CodeQL analysis workflow using GitHub's recommended query suites.


**Remediation effort:** LOW

**Data migration consideration:** No finding history can be migrated. A new CodeQL baseline scan must be run post-migration.

---

### 10. Multi-File Snippets (`snippets.multi_file`)
**Category:** snippets

**Source behavior:** GitLab snippets support multiple files within a single snippet. Each file has its own name and content.

**Target behavior:** GitHub Gists support multiple files in a single Gist, but the feature is limited compared to GitLab snippets. Files share a flat namespace within the Gist.

**Impact:** HIGH — GitLab multi-file snippets with directory structure cannot be directly represented in a GitHub Gist.

**Workaround:** Use a single Gist with multiple files; file organization must be managed by naming convention rather than directory structure.

**Remediation effort:** MEDIUM

**Data migration consideration:** Content is preserved; directory structure and grouping metadata are lost.

## 3. 🟡 Behavioral Differences
### 1. IP Allowlist (`access.ip_allowlist`)
**Category:** access_control

GitLab groups support IP restriction lists. Access to the group and its projects is denied for requests outside the configured CIDR ranges. -> GitHub Enterprise Cloud organizations and enterprises support IP allowlists restricting access to specific CIDR ranges.

**Action required:** Review and validate behavior before migration.

---

### 2. Team / Group Hierarchy (`access.team_hierarchy`)
**Category:** access_control

GitLab groups support arbitrary nesting depth (subgroups within subgroups). Permissions cascade from parent to child groups. Projects inherit group-level members and permissions. -> GitHub organizations support nested teams (parent-child teams). Permission inheritance works for child teams. However, organizations have only one level — there is no subgroup equivalent to GitLab's multi-level group nesting.

**Action required:** Deep group hierarchies must be flattened into GitHub teams with naming conventions. Inherited permissions from multi-level groups must be manually reconstructed. This is one of the most labor-intensive manual steps in a GitLab-to-GitHub migration.


---

### 3. Pipeline Artifacts (`cicd.artifacts`)
**Category:** cicd

GitLab artifacts are files produced by jobs. They can be passed between jobs in the same pipeline, downloaded from the UI, and have configurable expiry. -> GitHub Actions artifacts can be uploaded and downloaded within a workflow run using actions/upload-artifact and actions/download-artifact. Default retention is 90 days.

**Action required:** LOW for most use cases. Release artifacts should be published to GitHub Releases rather than relying on Actions artifact storage.


---

### 4. Deployment Environments (`cicd.environments`)
**Category:** cicd

GitLab environments track deployment state with a deployment history per environment. Environments can have deployment rules, required approvals, and protected status. -> GitHub Actions environments track deployment history per environment. Environments can have required reviewers, wait timers, and deployment branch policies.

**Action required:** Environments must be manually recreated with the correct protection rules and secrets. GitLab deployment history is not migratable to GitHub.


---

### 5. CI/CD Pipelines (`cicd.pipelines`)
**Category:** cicd

GitLab CI/CD pipelines are defined in .gitlab-ci.yml. They support stages, jobs, DAG-based ordering, parent-child pipelines, and multi-project pipelines. -> GitHub Actions workflows are defined in .github/workflows/*.yml. They support jobs, steps, reusable workflows, matrix strategies, and conditional expressions.

**Action required:** All CI/CD pipeline configurations must be fully rewritten from .gitlab-ci.yml to GitHub Actions YAML. This is one of the most significant migration efforts.


---

### 6. CI/CD Runners (`cicd.runners`)
**Category:** cicd

GitLab supports shared runners (hosted by GitLab), group runners, and project runners. Runners are registered with a token and can be tagged. -> GitHub supports GitHub-hosted runners (various OS flavors) and self-hosted runners. Runners are registered at repository, organization, or enterprise level.

**Action required:** MEDIUM. Runner infrastructure must be re-registered with GitHub. Self-hosted runner images may need updating to use the GitHub Actions runner agent instead of GitLab Runner.


---

### 7. Webhooks (`integrations.webhooks`)
**Category:** integrations

GitLab supports project, group, and system-level webhooks. Webhooks can be triggered by a wide range of events and support custom headers and SSL verification settings. -> GitHub supports repository, organization, and GitHub App webhooks. Webhooks fire on a configurable set of events. GitHub supports payload delivery tracking and redeliver.

**Action required:** Review and validate behavior before migration.

---

### 8. Label Case Sensitivity (`labels.case_sensitivity`)
**Category:** labels

GitLab label names are case-insensitive. "Bug" and "bug" are treated as the same label. This can cause confusion during migrations to platforms with case-sensitive labels. -> GitHub label names are case-insensitive for matching but preserve the case in which they were created. Attempting to create a label that differs only by case will result in a conflict.

**Action required:** MEDIUM — Target platforms with case-sensitive labels may create duplicate labels during import.

---

### 9. Maven / Gradle Package Hosting (`packages.maven`)
**Category:** packages

GitLab Package Registry hosts Maven artifacts. Supports both project-level and group-level repositories. Standard Maven settings.xml configuration required. -> GitHub Packages hosts Maven and Gradle packages. Authentication uses GITHUB_TOKEN. The repository URL format differs from GitLab; settings.xml or build.gradle must be updated.

**Action required:** Review and validate behavior before migration.

---

### 10. npm Package Hosting (`packages.npm`)
**Category:** packages

GitLab Package Registry hosts npm packages at the project or group scope. Packages are published using the standard npm publish command with GitLab registry URL. -> GitHub Packages hosts npm packages scoped to a user, organization, or repository. Authentication uses GITHUB_TOKEN or PAT. Package URLs differ from GitLab registry URLs.

**Action required:** Review and validate behavior before migration.

---

### 11. NuGet Package Hosting (`packages.nuget`)
**Category:** packages

GitLab Package Registry hosts NuGet packages at project or group scope. Compatible with dotnet CLI and NuGet CLI. -> GitHub Packages hosts NuGet packages. Authentication uses GITHUB_TOKEN. The package source URL and nuget.config must be updated to point to GitHub's registry.

**Action required:** Review and validate behavior before migration.

---

### 12. Project Boards / Kanban (`pm.boards`)
**Category:** project_management

GitLab boards are per-project and per-group Kanban boards. Boards use labels as columns. Multiple boards per project are supported (Premium+). Group boards aggregate issues across projects. -> GitHub Projects v2 provides Kanban board views with configurable fields, filters, and grouping. Projects are organization-scoped and linked to issues/PRs via metadata rather than label-based columns.

**Action required:** Review and validate behavior before migration.

---

### 13. Milestones (`pm.milestones`)
**Category:** project_management

GitLab milestones can be scoped to projects or groups. Milestones track progress via issue and MR counts. Group milestones aggregate across projects. -> GitHub milestones are scoped to individual repositories. There is no organization-level or cross-repository milestone.

**Action required:** Review and validate behavior before migration.

---

### 14. Container Registry (`repo.container_registry`)
**Category:** repository

GitLab has a built-in container registry (registry.gitlab.com) co-located with each project. Supports Docker V2 and OCI image formats. Supports cleanup policies. -> GitHub Container Registry (ghcr.io) is a standalone OCI-compliant container registry. Supports Docker V2, OCI images, and multi-arch manifests. Linked to GitHub packages.

**Action required:** All container image references in Dockerfiles, Kubernetes manifests, Helm charts, and CI pipelines must be updated to the new ghcr.io URLs. Image retention policies must be reimplemented via API or third-party tooling.


---

### 15. Package Registry (`repo.packages`)
**Category:** repository

GitLab Package Registry supports npm, Maven, PyPI, NuGet, Conan, Helm, Composer, and generic packages. All packages are scoped to a project or group. -> GitHub Packages supports npm, Maven, Gradle, NuGet, RubyGems, and Docker/OCI. Does not natively support PyPI, Helm, Conan, or Composer. Packages are scoped to repositories or organizations.

**Action required:** Projects using unsupported package formats must be migrated to an alternative external registry. All CI pipeline publish steps and consumer pip/helm install commands must be updated.


---

### 16. Protected Branches (`repo.protected_branches`)
**Category:** repository

GitLab protected branches allow per-role push/merge/force-push restrictions. Roles include Maintainer, Developer, No one. Multiple protection rules can coexist. -> GitHub protected branches enforce required status checks, required reviews, signed commits, and push restrictions. Rules apply per-branch pattern.

**Action required:** All branch protection rules must be manually recreated on GitHub. Automated migration of protection rules from GitLab is not feasible without custom tooling.


---

### 17. Approval Rules (`review.approval_rules`)
**Category:** code_review

GitLab supports named approval rules per merge request. Rules can require approvals from specific users, groups, or code owners. Eligible approvers and minimum approval count are configurable. -> GitHub required reviews are configured via branch protection or rulesets. A minimum number of approving reviews can be required before merging. Named approval rules (as in GitLab) are not a concept — all approvals are counted toward a single threshold.

**Action required:** Complex multi-rule approval workflows cannot be directly replicated on GitHub. Approval governance structures must be redesigned for the GitHub model.


---

### 18. Code Owners (`review.code_owners`)
**Category:** code_review

GitLab supports a CODEOWNERS file (or .gitlab/CODEOWNERS). Code owners are automatically added as required approvers when their owned paths are changed. -> GitHub supports a CODEOWNERS file in the root, .github/, or docs/ directory. Code owners are auto-requested for review when their paths change. Syntax differs from GitLab in some edge cases.

**Action required:** CODEOWNERS files must be reviewed and updated. Group/team references must be converted from GitLab namespace syntax to GitHub @org/team syntax.


---

### 19. Merge Strategies (`review.merge_strategies`)
**Category:** code_review

GitLab supports merge commit, squash and merge, and fast-forward merge strategies. The allowed strategy can be configured per project. -> GitHub supports merge commit, squash and merge, and rebase and merge strategies. The allowed strategies can be configured per repository.

**Action required:** Review and validate behavior before migration.

---

### 20. Multiple Assignees (`review.multiple_assignees`)
**Category:** code_review

GitLab allows multiple assignees on merge requests and issues. There is no hard cap on the number of assignees. -> GitHub allows multiple assignees on pull requests and issues, but is limited to a maximum of 10 assignees per issue or pull request.

**Action required:** LOW for most teams. Only affects projects with unusually broad issue ownership. Assignee truncation is silent and may go unnoticed.


---

### 21. Audit Log (`security.audit_log`)
**Category:** security

GitLab provides audit events at group and instance level. Events cover user actions, permission changes, and administrative operations. Available via UI and API. -> GitHub provides audit logs at the organization and enterprise level accessible via UI and API/streaming. Events cover user actions, repo changes, and admin operations.

**Action required:** Review and validate behavior before migration.

---

### 22. Custom Secret Detection Patterns (`security.custom_secret_patterns`)
**Category:** security

GitLab secret detection supports extending detection logic with custom rulesets for organization-specific patterns (tier-dependent). -> GitHub Advanced Security supports custom secret scanning patterns in addition to built-in detectors. Availability depends on Advanced Security enablement.

**Action required:** Review and validate behavior before migration.

---

### 23. Dependency Scanning (`security.dependency_scanning`)
**Category:** security

GitLab provides dependency scanning as CI jobs, detecting vulnerabilities in project dependencies across many ecosystems. -> GitHub Dependabot provides dependency vulnerability scanning, automated alerts, and automated PRs to update vulnerable dependencies.

**Action required:** Review and validate behavior before migration.

---

### 24. Secret Detection (`security.secret_detection`)
**Category:** security

GitLab includes built-in secret detection as part of GitLab Secure. Scans are run as CI jobs and results appear in the merge request security report. -> GitHub provides secret scanning for public repositories and GitHub Advanced Security (GHAS) for private repositories. Push protection can block commits containing secrets.

**Action required:** Review and validate behavior before migration.
