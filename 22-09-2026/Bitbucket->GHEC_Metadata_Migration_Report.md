# Bitbucket Cloud → GitHub Enterprise Cloud (GHEC) Metadata Migration / Parity Report

---

## 1. Executive Summary

This report presents an exhaustive metadata-level parity analysis between **Bitbucket Cloud** (source) and **GitHub Enterprise Cloud (GHEC)** (target) for the purpose of engineering a custom migration solution. The analysis covers every meaningful metadata item, configuration surface, and capability across repositories, workspaces/projects, users/permissions, branches/tags, pull requests/reviews, issues/project management, CI/CD, deployments, packages, integrations, security, governance, wiki, and collaboration features.

**Master Inventory Summary:**

| Classification | Count |
| --- | ---: |
| 🟢 Seamless / Direct Migrations | 44 |
| 🟡 Migratable with Changes / Behavioral Differences | 112 |
| 🔴 Hard Blockers / Cannot Be Migrated | 19 |
| **Total Unique Metadata/Capabilities** | **175** |

**Key Findings:**

1. **Core Git data** (commits, branches, tags, LFS objects, submodules) transfers with high fidelity. Repository-level descriptive metadata (name, description, visibility, default branch) is largely seamless.

2. **Organizational structure** requires significant transformation. Bitbucket's three-tier hierarchy (Workspace → Project → Repository) does not map directly to GHEC's hierarchy (Enterprise → Organization → Repository with Teams). Projects in Bitbucket carry permissions and grouping semantics that must be decomposed into GHEC Organizations, Teams, and repository grouping conventions.

3. **Permissions and access control** require substantial re-engineering. Bitbucket's workspace roles, project permissions, group model, and repository-level grants differ from GHEC's enterprise/organization/team/repository permission model, custom roles, and outside-collaborator concept.

4. **Pull request metadata** is migratable but requires careful transformation of reviewers, approvals, tasks, default-reviewer rules, and merge-check semantics. Historical PR data (comments, activity, approvals) can be recreated via API but with altered actor attribution and timestamps.

5. **CI/CD** (Bitbucket Pipelines → GitHub Actions) requires a full rewrite of pipeline definitions. Variables, secrets, environments, deployment gates, runners, caches, artifacts, and schedules all have GHEC equivalents but with different configuration models.

6. **Issues and project management** differ significantly in data model, workflow, fields, and scope. Bitbucket Cloud issues are repository-scoped with fixed fields (kind, priority, component, milestone, version); GitHub Issues use labels, milestones, issue types (beta), and GitHub Projects for workflow tracking.

7. **Security features** (secret scanning, code scanning, dependency scanning) exist on both platforms but are different products with different configuration, and Bitbucket Cloud's native security scanning is limited compared to GHEC with GitHub Advanced Security (GHAS).

8. **Hard blockers** are concentrated in areas where Bitbucket Cloud has a unique capability with no GHEC equivalent (e.g., Bitbucket Snippets, Bitbucket Pipes ecosystem references, pipeline build-minute quotas, certain Jira-native integration depth) or where historical operational data (pipeline run history, deployment history, audit logs) cannot be natively imported into GHEC's data stores.

## 3. 🟡 Migratable with Changes / Behavioral Differences

These metadata items have comparable capabilities on both platforms but require transformation of data model, scope, configuration, permissions, semantics, or workflow. Historical data may be partially preservable. Actor attribution and timestamps may shift. All items in this section have a reasonable migration or recreation path.

## 5. Conditions and Assumptions

### 5.1 Conditions Applicable to Seamless Migrations

1. **GHEC Enterprise Policy Alignment**: Several seamless migrations (particularly repository visibility) depend on GHEC enterprise and organization policies being configured to permit the equivalent setting. For example, if the GHEC enterprise policy prohibits public repositories, a public Bitbucket repository cannot be migrated as public without a policy change.

2. **Git Protocol Fidelity**: All Git object data (commits, trees, blobs, tags, notes, replace refs) transfers with byte-level fidelity via standard Git operations (`git clone --mirror` / `git push --mirror`). SHA integrity is preserved. This is the foundation for classifying core Git data as seamless.

3. **LFS Storage Quotas**: Git LFS data transfers correctly but consumes GHEC storage quota. Each GHEC organization receives a base LFS storage allocation (1 GiB for the organization, with data packs available for purchase). Large LFS stores must be planned for quota impact.

4. **Author Attribution on UI**: While Git commit author/committer metadata (name, email, timestamp) transfers with perfect fidelity at the Git data level, the GHEC **UI attribution** (linking commits to GitHub user profiles, showing avatars) depends on whether the commit email addresses are associated with GitHub accounts. This is a UI/display concern, not a data integrity concern.

5. **Repository Naming Constraints**: Bitbucket Cloud allows repository names up to 128 characters; GHEC allows up to 100 characters. Bitbucket slugs may contain characters not allowed in GitHub repository names. In practice, the vast majority of repository names are compatible. A pre-migration validation pass should identify any names requiring adjustment.

6. **Markdown Compatibility**: Both platforms use Markdown for PR descriptions, comments, READMEs, and wiki content. Bitbucket uses a variant that is largely compatible with GitHub Flavored Markdown (GFM). Differences exist in:
   - @mention syntax (Bitbucket uses `@{account_id}` internally; GitHub uses `@username`)
   - Internal link formats
   - Some advanced formatting (panels, macros, etc., if using Bitbucket's rich editor)
   
   For items classified as "seamless," the core text content transfers; any Bitbucket-specific syntax embedded in the content is a content-transformation concern documented in the behavioral-differences section.

7. **Timestamps**: Repository-level timestamps (`created_at`, `updated_at`) on GHEC will reflect the migration time, not original Bitbucket timestamps. Git-level timestamps (commit dates) are preserved. If original Bitbucket timestamps are required for compliance or auditing, they should be captured from the Bitbucket API before migration and stored externally or in a metadata repository.

8. **Empty Repositories**: Both platforms handle empty repositories, but some GHEC API operations require at least one commit. If a Bitbucket repository is empty, it can be created empty on GHEC; however, branch protection rules and other settings require at least one branch to exist.

### Scope of "Seamless"

Items in this table require:
- No data-model transformation
- No permission restructuring
- No scope remapping
- No behavioral adaptation
- At most, trivial field-name mapping (e.g., `website` → `homepage`)

Items requiring any meaningful transformation—even if the target capability exists—are classified under 🟡 (Migratable with Changes).

### 5.2 Conditions Applicable to Behavioral Differences

#### Migration Prerequisites

1. **User Identity Mapping**: A comprehensive user mapping (Bitbucket accountId → GitHub username or EMU short-name) is a foundational prerequisite for virtually all metadata migration involving actor attribution (PRs, comments, reviews, approvals, issues, memberships). Migration will not succeed at scale without this mapping.

2. **Target Enterprise & Organization Provisioning**: GHEC enterprise (if new) and organizations (target of each workspace) must exist before repository migration. Organization settings, policies, SSO, SCIM, and enterprise policies should ideally be configured before user provisioning.

3. **GHAS Licensing**: Several security features—Secret Scanning (private repos), Code Scanning (private repos), and Dependency Review—require GitHub Advanced Security. If GHAS is not licensed, these behavioral parities are reduced.

4. **Actions Adoption**: CI/CD migration assumes commitment to migrating from Bitbucket Pipelines to GitHub Actions. Alternative approaches (keeping Pipelines pointed at GHEC via CI status API) are possible but not covered in the standard target state.

5. **API Rate Limits**: Bulk migration via API is subject to GHEC rate limits (5000 requests/hour authenticated, higher with GitHub Apps). Bulk imports of large numbers of issues/PRs/comments must implement backoff and possibly use GitHub Apps for higher throughput.

6. **EMU vs Standard GHEC**: The choice of Enterprise Managed Users (EMU) vs standard GHEC organization membership significantly affects user mapping strategy, invitation flow, and identity model. Decision must be made before migration begins.

#### Behavioral Change Impacts on Users

1. **Cross-Reference Rewriting**: Bitbucket issue/PR IDs will change during migration (due to GitHub's shared counter for issues and PRs). All in-content cross-references (`#123`, `workspace/repo#456`) require transformation using a comprehensive mapping table. External systems referencing Bitbucket URLs need reconfiguration.

2. **Actor Attribution in Migrated Content**: When recreating PRs, comments, issues, or reviews via GHEC API, the API caller becomes the "author" of the object. Original author attribution must be preserved either:
   - By impersonating each user (requires user tokens — not scalable)
   - By using GHEC's import API with pre-migration attribution
   - By prepending author metadata to content bodies (e.g., `*Originally by @user on 2023-01-01*`)
   - By using a "migration bot" account uniformly with author annotations
   
   Choice affects the fidelity of historical audit trails.

3. **Timestamp Fidelity**: Native `created_at` / `updated_at` on migrated PRs, issues, and comments will reflect migration time. Original timestamps preservable only via body annotations or via GHEC's specialized import mechanisms. Git commit timestamps are preserved.

4. **Webhook Payload Structure**: Consumers of Bitbucket webhooks must be rewritten to parse GHEC's completely different payload structure (different field names, event catalog, signature scheme). Direct payload compatibility is not achievable.

5. **CI/CD Pipeline Rewrite**: `bitbucket-pipelines.yml` files must be rewritten as GitHub Actions workflows. No automated 1:1 translation exists (though converter tools can accelerate this). Migrated workflows should be tested end-to-end before cutover.

### 5.3 Conditions Applicable to Hard Blockers

1. **Historical vs. Ongoing Capability Distinction**: The blockers in this section are almost exclusively about **historical runtime data** (pipeline runs, deployment records, audit events, webhook deliveries, review timestamps). The **ongoing capabilities** in the equivalent areas are usually achievable through 🟡-classified reconfiguration (e.g., GitHub Actions replaces Bitbucket Pipelines as ongoing CI capability, even though historical pipeline runs are a blocker).

2. **External Cold Storage as Standard Compromise**: For most historical data blockers, the standard engineering compromise is:
   - Export the Bitbucket-side data via API before decommissioning source
   - Store it in accessible archive form (S3, dedicated read-only app, SIEM)
   - Retain the source Bitbucket instance in read-only mode for a grace period if licensing/contract permits
   - Provide external reference links from GHEC repos (e.g., in README) if needed
   
   This does not restore native platform behavior but preserves data for compliance, forensics, and reference.

3. **Actor Attribution Fidelity is a Fundamental Public-API Limitation, Not a Missing Feature**: The inability to set original author identities and original timestamps on migrated objects via the standard GHEC public REST/GraphQL API is a deliberate integrity property of the GHEC data model (the API records the acting principal, not an arbitrary asserted identity). Any migration solution using only public APIs will inherit this limitation. Custom migration solutions cannot circumvent it without special import mechanisms.

4. **Bitbucket Pipes Ecosystem Requires Case-by-Case Mapping**: There is no authoritative Atlassian-published or GitHub-published mapping from Bitbucket Pipes to GitHub Actions. Each `pipe:` reference in every `bitbucket-pipelines.yml` requires human evaluation to identify a functionally equivalent GitHub Action, evaluate its security/maintenance posture, and adapt inputs/outputs.

5. **Jira Historical Links Are a Cross-Platform Blocker**: The Jira Development Panel's historical Bitbucket references are stored on Atlassian's Jira side and can only be rewritten via Jira-side automation (Jira API + Development Information API). This is outside the scope of a GHEC-side migration tool and requires coordinated Jira administration.

6. **Downloads URL Consumer Impact Requires Migration Communication**: Any external system (installers, package managers, third-party projects) that hardcodes Bitbucket Downloads URLs will fail after Bitbucket decommissioning. A pre-migration audit of well-known consumers (Homebrew formulas, apt/yum repositories, deployment scripts) is essential.

7. **Redirect / URL Rewriting Requires External Infrastructure**: Bitbucket does not provide a durable URL redirect service post-decommissioning. If URL stability across the migration boundary is required, deploy an external redirect/CDN service under a stable custom domain that proxies to GHEC URLs.

## 6. Key Migration Observations

### Structural / Data-Model Observations

1. **Workspace → Organization is a lossy mapping when Projects are heavily used.** Bitbucket's Project layer performs both permission-grouping and repository-grouping. GHEC has no direct equivalent, requiring decomposition into (Teams for permissions) + (Topics/Custom Properties for grouping). Custom properties are strongly recommended as they enable Ruleset targeting.

2. **The PR data model is materially compatible but attribution is the hardest problem.** PR titles, descriptions, source/target branches, states, and comments map cleanly. However, preserving original author, reviewer, and approval attribution requires either GitHub's import mechanism, per-user impersonation, or body-annotation compromises.

3. **Issues require a labeling strategy design decision.** Bitbucket's issue schema (kind, priority, component, version, status) is richer than GitHub's native issue schema. A pre-migration labeling convention must be designed (e.g., `type:*`, `priority:*`, `component:*`, `version:*` labels) and applied consistently across all migrated repositories.

4. **Bitbucket Project keys should be preserved as custom repository properties.** Because Bitbucket project keys often appear in commit messages, branch names, and Jira integration references, capturing them as GHEC custom properties enables downstream systems to continue resolving them.

### CI/CD Observations

5. **Pipeline migration is the largest engineering effort in most Bitbucket → GHEC migrations.** Every `bitbucket-pipelines.yml` requires translation. Common patterns (build, test, deploy) translate well; complex patterns (dynamic pipelines, deep parallelism, custom Docker images) require careful design. Investment in a converter tool with human review is typically justified.

6. **Secrets values cannot be migrated automatically.** All secured variables at repo, workspace, and deployment scope must be re-obtained from their original sources (vaults, config repos, manual entry). A pre-migration inventory of secret usage is essential.

7. **OIDC federation reconfiguration is often overlooked.** Cloud provider trust policies (AWS IAM roles, GCP workload identity, Azure federated credentials) must be updated with the GHEC OIDC issuer and claim mappings. This is a cross-team coordination item.

8. **Runner architecture change requires infrastructure re-work for self-hosted CI.** Bitbucket runners are Docker containers; GHEC runners are installed agents (or containerized with GHCR). Runner group configuration, autoscaling, and lifecycle management must be redesigned.

### Access & Permissions Observations

9. **Access token strategy must shift from App Passwords / Repository Access Tokens to GitHub Apps.** Bitbucket's scoped access tokens (repo/project/workspace) have no direct GHEC user-independent equivalent. GitHub Apps with fine-grained repo/org permissions are the recommended replacement and require deliberate design of installation scope.

10. **Group → Team mapping is straightforward, but IdP sync should be reconsidered.** If IdP sync is available (Okta, Azure AD), consider mapping directly to IdP groups → GHEC teams via SCIM/SAML sync rather than a snapshot migration. This provides ongoing identity management.

11. **Outside collaborators are a GHEC-specific concept useful for external contractors.** Users who currently have single-repo access in Bitbucket (via direct repo permission) may be appropriate outside collaborators rather than org members, reducing org member counts and license costs.

### Security & Governance Observations

12. **Security scanning migration is greenfield.** Historical alerts, findings, and remediation records from Bitbucket-side scanning are not portable. Plan to remediate outstanding critical findings pre-migration and start fresh scanning on GHEC (with GHAS as needed).

13. **Audit log continuity requires external streaming, not migration.** Since GHEC audit logs cannot be back-populated, plan to export the Bitbucket audit log to your SIEM before migration and configure GHEC audit log streaming to the same SIEM immediately post-migration to maintain continuity.

14. **Ruleset-based enforcement is significantly more powerful than branch protection.** For any organization migrating meaningful branch restrictions, invest time in designing Rulesets targeting via custom properties rather than reproducing legacy per-repo branch protection rules.

### Integration Observations

15. **Jira integration works well post-migration but requires re-linking.** The GitHub for Jira app provides feature-comparable Jira integration to Bitbucket's native integration. However, historical Jira ↔ Bitbucket links will not automatically rewrite to point at GHEC; those historical dev-panel entries remain as Bitbucket references.

16. **Every webhook consumer needs code changes.** Webhook URL, secret, event names, and payload structure all change. Plan a webhook consumer inventory and rewrite phase in parallel with repository migration.

17. **OAuth apps and third-party integrations require credential rotation and endpoint updates.** No OAuth secrets or tokens migrate. Any application using Bitbucket OAuth needs to be rebuilt against GHEC OAuth or GitHub Apps.

### Practical Sequencing Observations

18. **Recommended migration phase order:**
    1. Provision GHEC enterprise, orgs, SSO, SCIM
    2. Provision users (SCIM/invite)
    3. Configure enterprise/org policies, custom properties, teams
    4. Migrate repositories (Git data first)
    5. Migrate repository metadata (settings, collaborators, deploy keys)
    6. Migrate branch protection / rulesets
    7. Migrate PR data (open PRs first, then closed for archival)
    8. Migrate issues
    9. Migrate wiki content
    10. Migrate CI/CD (Actions workflows, secrets, environments)
    11. Migrate webhooks and reconfigure consumers
    12. Configure security scanning
    13. Cutover: freeze Bitbucket, final delta migration, redirect users

19. **Cutover strategy is critical.** For active repositories with in-flight PRs/pipelines, plan a read-only freeze window on Bitbucket while performing final delta migration. Consider running Bitbucket in read-only mode for a grace period for reference.

### Observations Specific to Hard Blockers

1. **The Blocker Set is Concentrated in Runtime/Historical Data, Not Configuration**: With very few exceptions (Bitbucket Pipes ecosystem, snippet ownership model), the hard blockers are not missing GHEC features—they are missing paths to inject historical runtime data into GHEC's data stores. This is architecturally deliberate on GHEC's side and is not a gap that will close via new APIs.

2. **The Migration Solution Must Include an "External Archive" Component**: Because so many blockers resolve to "data preservable externally," a production-grade Bitbucket → GHEC migration solution should include, as a first-class component, a metadata/artifact archive service that:
   - Extracts pipeline history, deployment history, audit logs, webhook delivery logs, and any other blocker-class historical data via Bitbucket APIs
   - Stores extracted data in queryable form (S3 + metadata index, or a purpose-built archive DB)
   - Publishes stable read-only URLs that can be referenced from migrated GHEC repos where historical continuity is important
   
   Migrations that skip this component leave compliance and forensic gaps.

3. **CI/CD Migration is Two Simultaneous Tracks**: The pipeline-configuration rewrite (🟡 class) and the runtime-history archive (🔴 class) are independent workstreams that must proceed in parallel. Attempting to do them sequentially significantly extends migration timeline.

4. **Actor Attribution Compromise Must Be an Explicit Design Decision**: Every migration solution must choose one of:
   - **Migration bot uniform**: Simplest; all migrated objects appear authored by a single bot account with body annotations for original authors. Low fidelity, low complexity.
   - **Per-user impersonation**: Highest fidelity for author identity; requires each user to supply a PAT to the migration tool; not scalable beyond dozens of users; security concerns around token custody.
   - **Ghost user pattern**: Placeholder GitHub users for departed original users, real users for active ones. Compromise middle-ground.
   
   This decision affects every migrated PR, issue, comment, and review, and must be made before any migration code is written.

5. **URL Stability Is Not a Native GHEC Feature — Design for It Externally**: Bitbucket URLs across every feature (repo pages, PR pages, issue pages, downloads, snippets, wiki, pipeline run pages) all cease to work at Bitbucket decommissioning. Any external system, documentation, email archive, wiki, or third-party consumer with hardcoded Bitbucket URLs will break. If URL continuity matters, plan for a durable redirect service under a controlled domain that translates Bitbucket URL patterns to GHEC equivalents using the migration mapping table.

6. **Regulated/Compliance-Sensitive Environments Face the Highest Blocker Impact**: The blockers most impactful in regulated environments are:
   - Historical PR approval timestamps and original approver identity (row 10)
   - Historical audit log continuity (row 13)
   - Historical deployment records with authentic actors/times (row 8)
   
   For SOX, HIPAA, PCI-DSS, or similarly-regulated organizations, plan for extended parallel operation of Bitbucket (read-only) alongside GHEC to preserve immutable audit trail access, and configure external SIEM streaming from both platforms during the transition period.

7. **Some "Blockers" Are Really Ecosystem Substitutions, Not Feature Gaps**: The Bitbucket Pipes → GitHub Actions Marketplace transition (row 5) is not a feature gap—both are rich ecosystems of pre-built integrations—but the substitution work is substantial. Budget explicit engineering time for it. Consider maintaining an internal Pipes-to-Actions mapping registry that captures decisions once for reuse across many repositories.

8. **The Jira Historical Link Blocker Requires Jira-Side Investment**: Organizations heavily invested in Bitbucket-Jira integration should scope a Jira-side link rewrite project separately from the GHEC migration itself. This uses Jira's REST API and Development Information API to walk historical issues, identify Bitbucket references, and rewrite them to GHEC equivalents using the migration mapping table. This is often deferred or scoped out but represents real ongoing operational drag if not addressed.

9. **Enterprise Migration Cutover Must Include a "Freeze Window" Design**: Because none of the blocker-class data can be delta-migrated after cutover (audit logs, webhook deliveries, pipeline runs continue to accrue on Bitbucket during migration and cannot be back-ported), plan a clear read-only freeze on Bitbucket at cutover time to draw a clean line between "before" data (in Bitbucket) and "after" data (in GHEC). During the freeze:
   - Perform final delta Git sync
   - Perform final delta PR/issue sync
   - Perform final export of blocker-class historical data
   - Redirect DNS/URLs
   - Switch consumers (webhooks, integrations, CI triggers)
   - Enable GHEC audit log streaming

10. **The 175-Item Master Inventory Distributes Approximately 25% / 64% / 11% Across Classifications**: 
    - 🟢 Seamless (44 items, ~25%): Core Git data and simple repo metadata
    - 🟡 Migratable with Changes (112 items, ~64%): The bulk of the migration engineering work
    - 🔴 Hard Blockers (19 items, ~11%): Historical runtime data + ecosystem substitutions
    
    This distribution should inform migration project sizing: the seamless bucket is a small portion of the effort (though it's the biggest data volume), the middle bucket is where the migration solution's engineering complexity lives, and the blocker bucket requires organizational risk acceptance and external archive investment.
