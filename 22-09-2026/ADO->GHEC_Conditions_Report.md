# Azure DevOps (ADO) → GitHub Enterprise Cloud (GHEC) Conditions & Assumptions Mapping

Below is a consolidated extraction of every condition and assumption from all three parts of the report, mapped to the specific metadata items or attributes they govern, what each condition checks, and whether it is already surfaced in the current discovery.

---

## Part 1 — Conditions from 🟢 Seamless / Direct Migrations

| # | Condition | What It Checks | Metadata / Attribute(s) Affected | Available in Current Discovery |
|---|---|---|---|---|
| 1 | **Git Data Transfer Mechanism** | Verifies that all Git-native objects are transferred via `git clone --mirror` / `git push --mirror` or equivalent to preserve SHA fidelity, author info, signatures, and ref integrity. | `repo.commits`, `repo.branches`, `repo.tags`, `repo.commit_signatures`, `repo.submodules`, `repo.lfs_pointers`, `repo.gitignore`, `repo.gitattributes`, `repo.license`, `repo.readme`, `wiki.git_repo` | ✅ Yes — documented in Response 1, Condition 1 |
| 2 | **LFS Storage Quotas** | Checks that total LFS object store size per repository fits within GHEC quotas (1 GB storage + 1 GB/month bandwidth included; 2 GB per-file limit). | `repo.lfs_objects`, `repo.lfs_pointers` | ✅ Yes — Response 1, Condition 2 |
| 3 | **Repository Size Limits** | Checks that Git data (excluding LFS) per repository is within GHEC's recommended 5 GB soft limit and that no single file exceeds 100 MB (hard push limit). | `repo.name`, `repo.commits`, `repo.branches`, `repo.tags` | ✅ Yes — Response 1, Condition 3 |
| 4 | **Identity Mapping Prerequisite** | Checks that a definitive mapping between ADO user identities (Entra ID UPN/objectId/MSA) and GHEC accounts (login) exists before any user-referencing metadata is migrated. | `review.pr_creator`, `review.pr_comment_text`, `pm.wi_comments`, `pm.mentions`, `access.users`, `access.memberships` | ✅ Yes — Response 1, Condition 4; also cross-referenced in Response 2, Condition 2 |
| 5 | **Organization Name Compatibility** | Checks that the target GHEC org name meets GitHub naming rules (1–39 chars, alphanumeric + hyphens, no leading/trailing/consecutive hyphens). | `org.metadata`, `org.display_name` | ✅ Yes — Response 1, Condition 5 |
| 6 | **Repository Name Compatibility** | Checks that ADO repo names are sanitized to meet GHEC naming rules (alphanumeric, hyphens, underscores, periods; no leading period; `.git`/`.github` reserved). | `repo.name` | ✅ Yes — Response 1, Condition 6 |
| 7 | **Fork Relationship Establishment** | Checks that forked repos are created via GitHub Fork API (`POST /repos/{owner}/{repo}/forks`) after the parent is migrated, not via independent push, to preserve the fork network. | `repo.forks` | ✅ Yes — Response 1, Condition 7 |
| 8 | **Markdown Dialect Compatibility** | Checks for ADO-specific Markdown extensions (`[[_TOC_]]`, `:::mermaid`, `@<GUID>`, `#<WI-ID>`, `/.attachments/` paths) that render differently or not at all on GFM. | `review.pr_description`, `review.pr_comment_text`, `pm.work_item_description`, `pm.wi_comments`, `wiki.page_content`, `repo.markdown_rendering` | ✅ Yes — Response 1, Condition 8 |
| 9 | **Wiki Repository Structure** | Checks that ADO `.order` files are converted to `_Sidebar.md` and that wiki Git repo is initialized on GHEC before push. | `wiki.git_repo`, `wiki.order`, `wiki.page_content` | ✅ Yes — Response 1, Condition 9 |
| 10 | **Attachment Size Limits** | Checks that file attachments do not exceed GHEC limits (25 MB per file for issues/PRs, 10 MB for images in some contexts, 100 MB for videos). | `pm.attachments_content`, `pm.wi_attachments`, `review.pr_attachments` | ✅ Yes — Response 1, Condition 10 |
| 11 | **Azure DevOps Services Scope** | Checks that the analysis is scoped to ADO Services (cloud) and does not silently include ADO Server / TFS features. | All metadata items (scope qualifier) | ✅ Yes — Response 1, Condition 11; also enforced by the original task instructions |
| 12 | **GHEC Enterprise Tier** | Checks that GHAS-dependent features (CodeQL, secret scanning push protection, dependency review) are flagged as requiring separate GHAS licensing. | `security.code_scanning`, `security.secret_scanning`, `security.dependency_scanning` | ✅ Yes — Response 1, Condition 12 |

## Part 2 — Conditions from 🟡 Migratable with Changes / Behavioral Differences

| # | Condition | What It Checks | Metadata / Attribute(s) Affected | Available in Current Discovery |
|---|---|---|---|---|
| 13 | **Custom Migration Tooling Required** | Checks that off-the-shelf tools (GEI, `azure-devops-migration-tools`) are insufficient for comprehensive migration and that bespoke code is needed for WIs, boards, pipelines, service connections, and permissions. | All 🟡 items (cross-cutting) | ✅ Yes — Response 2, Condition 1 |
| 14 | **Identity Mapping is Cross-Cutting** | Checks that identity mapping is established before migrating any user-referencing metadata and that options (CSV, SCIM/EMU, admin API) are evaluated. | `access.users`, `access.memberships`, `access.sso`, `access.scim`, `access.emu`, `review.pr_creator`, `pm.wi_comments`, `pm.mentions` | ✅ Yes — Response 2, Condition 2 |
| 15 | **Timestamps Cannot Be Backdated Natively** | Checks that GHEC REST APIs set `created_at`/`updated_at` to API call time and that historical timestamps require workarounds (text prefix, Import API, or acceptance of migration timestamp). | `review.pr_created_date`, `pm.wi_comments`, `pm.wi_history`, `review.pr_history` | ✅ Yes — Response 2, Condition 3 |
| 16 | **API Rate Limits Constrain Throughput** | Checks that migration is batched with back-off to stay within GHEC rate limits (5,000 REST req/hr, 15,000 for GitHub App installations; 5,000 GraphQL points/hr; secondary rate limits). | All items migrated via API (cross-cutting) | ✅ Yes — Response 2, Condition 4 |
| 17 | **GHAS is a Separate Purchase** | Checks that GHAS features are not assumed included with GHEC Enterprise and that licensing is verified before planning security migration. | `security.code_scanning`, `security.secret_scanning`, `security.dependency_scanning` | ✅ Yes — Response 2, Condition 5 |
| 18 | **EMU Decision Impacts Everything** | Checks that the EMU vs. standard GHEC decision is finalized before migration begins, as it affects identity model, username format, and external contributor access. | `access.emu`, `access.sso`, `access.scim`, `access.users`, `access.memberships` | ✅ Yes — Response 2, Condition 6 |
| 19 | **Rulesets vs. Branch Protection** | Checks that Rulesets are preferred over classic Branch Protection for all branch/repo protection migration due to layering, bypass lists, and org-wide targeting. | `repo.branch_permissions`, `repo.branch_policy_reviewers`, `repo.branch_policy_build`, `repo.branch_policy_status`, `repo.branch_policy_bypass`, `repo.cross_repo_policies` | ✅ Yes — Response 2, Condition 7 |
| 20 | **Actions Marketplace Dependency** | Checks that equivalent GitHub Actions exist for each ADO pipeline task and that custom/niche tasks may require building custom actions or inlining scripts. | `cicd.steps`, `cicd.marketplace_tasks`, `cicd.pipelines_yaml` | ✅ Yes — Response 2, Condition 8 |
| 21 | **Environment Scope is Repo-Local** | Checks that GHEC environments are repository-scoped (not org-scoped) and that shared ADO environments must be recreated in each target repo. | `cicd.environments`, `cicd.environment_approvals`, `cicd.environment_checks`, `cicd.secrets` | ✅ Yes — Response 2, Condition 9 |
| 22 | **Package Format Coverage Gaps** | Checks that Python (PyPI) and Universal Packages are not natively supported by GitHub Packages and that alternate hosting is planned. | `packages.python`, `packages.universal`, `packages.feeds` | ✅ Yes — Response 2, Condition 10 |
| 23 | **Wiki Migration Uses Git** | Checks that wiki migration is performed as Git clone/push of `<repo>.wiki.git` and that the wiki is initialized on GHEC before push. | `wiki.git_repo`, `wiki.page_content`, `wiki.attachments` | ✅ Yes — Response 2, Condition 11 |
| 24 | **Historical Runs / Deployments Not Migrable Natively** | Checks that pipeline run history, build logs, deployment records, test results, and audit logs cannot be loaded into GHEC native structures and require external archival. | `cicd.pipeline_runs_history`, `cicd.logs`, `cicd.env_deployment_history`, `testing.test_run_history`, `security.audit_historical` | ✅ Yes — Response 2, Condition 12 |
| 25 | **CODEOWNERS Placement** | Checks that CODEOWNERS file is placed in `.github/`, `docs/`, or repo root AND that "Require review from Code Owners" is enabled in branch protection. | `repo.branch_policy_auto_reviewers`, `review.pr_required_reviewers`, `review.codeowners` | ✅ Yes — Response 2, Condition 13 |
| 26 | **Secret Values Must Be Re-Supplied** | Checks that all secret values (variable groups, service connections, secure files) require re-entry at target because source values are not retrievable via API. | `cicd.secrets`, `cicd.variable_groups`, `cicd.secure_files`, `cicd.service_connections_arm`, `cicd.service_connections_docker`, `cicd.service_connections_k8s`, `cicd.service_connections_generic`, `cicd.service_connections_pkg`, `cicd.sc_secret_values` | ✅ Yes — Response 2, Condition 14 |
| 27 | **Merge Queue Consideration** | Checks whether GHEC merge queue (Team/Enterprise) should be adopted as an alternative for complex build-validation + up-to-date branch policies. | `repo.branch_policy_build`, `repo.branch_policy_status`, `review.pr_merge_strategies` | ✅ Yes — Response 2, Condition 15 |
